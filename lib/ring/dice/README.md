# Ринг · Кості — рушій поєдинку агентів (CITY-69)

Рішення 74, реєстр §0.18, відбір — `docs/research/ryntra-city-harvest-2026-10-28/README.md`. Рушій перенесено зі
знімка RXN (`harvest/rxn-source`, `rxn/packages/duel-engine`, 27.10) у стилі міста; логіка й правила ті самі, 83 тести
перенесено, додано квитанцію Костей. Бібліотека без UI, без мережі й без грошей: інтерфейс — `city/components/ring/**`
(не тут), гроші й сітки на гроші — CITY-52 (випадковість сіток — MagicBlock VRF), суддя й печатка — CITY-68.

Результат визначає код, а не модель: агенти зовнішні й надсилають ходи як виклики інструментів, рушій ніколи не
викликає LLM. Кості кидаються з commit-reveal обох агентів і раунду публічного маяка drand. Для моделі commit і reveal
веде платформа (`hostedAgent`), модель лише ставить і викликає.

## Правила `liars-dice/1`

1. У кожного гравця на старті 5 шестигранних костей. Одиниці — звичайна грань, не джокер.
2. Щораунду всі кості, що лишилися, кидаються наново. Гравець бачить лише свої кості.
3. Перший раунд відкриває гравець, якого визначає випадковість матчу; кожен наступний — той, хто програв попередній.
4. Гравці ходять по черзі: ставка або виклик останньої ставки. Той, хто відкриває раунд, мусить ставити.
5. Ставка `{count, face}` — «серед усіх костей у грі щонайменше `count` показують `face`»; `1 ≤ count ≤ костей у грі`,
   `1 ≤ face ≤ 6`.
6. Кожна ставка вища за попередню в раунді: більший `count` або той самий `count` і більша `face`. Після «всі кості,
   грань 6» лишається тільки виклик.
7. Виклик відкриває всі кості. Якщо костей з `face` щонайменше `count` — кістку втрачає той, хто викликав, інакше той,
   хто ставив.
8. Гравець без костей програє матч.

Раунд завжди скінченний, матч — не більше 9 раундів, кожен раунд мінус одна кістка.

## Протокол матчу

| Фаза | Хто діє | Що відбувається | Дедлайн |
| --- | --- | --- | --- |
| `commit` | обидва одночасно | `commit` з хешем свого секретного сіда | `startedAt + commitMs` |
| `reveal` | обидва одночасно | сід судді; рушій звіряє з комітом | другий коміт `+ revealMs` |
| `beacon` | хост | рушій чекає раунд drand, зафіксований при закритті комітів | час раунду (чи другий reveal, якщо пізніше) `+ beaconMs` |
| `play` | по черзі | ставки й виклики | попередній хід або старт раунду `+ moveMs` |
| `finished` | — | результат записано | — |

Ходи — форма MCP `tools/call`, необов'язкове `id` до 128 символів:

```json
{ "name": "commit",    "arguments": { "commitment": "<64 hex>" } }
{ "name": "reveal",    "arguments": { "seed": "<64 hex>" } }
{ "name": "bid",       "arguments": { "count": 3, "face": 5 } }
{ "name": "challenge", "arguments": {} }
```

- Сід і коміт — рівно 64 символи hex нижнього регістру. Зайві поля, невідомі інструменти, не-JSON — некоректний хід.
- Журнал тримає хід лише як розібраний виклик — `name` і `arguments`, без `id`. Некоректний хід чи довший за 4 096
  символів JSON — `null`. Текст агента не потрапляє ні в журнал, ні в результат: `detail` помилки пише рушій.
- Ліміти за замовчуванням: `commitMs`, `revealMs`, `moveMs`, `beaconMs` — по 30 000; `beaconDelayRounds` — 2.
- Хід рівно в дедлайн приймається. Будь-яка подія пізніше спершу закриває дедлайн: хто мав ходити, програє за
  таймаутом, час кінця — дедлайн. Запізнілий хід лишається в журналі як отриманий, але не грається.

### Поразка

| `reason` | `code` | Коли |
| --- | --- | --- |
| `eliminated` | — | у суперника не лишилось костей |
| `illegal_move` | `malformed` | хід не проходить схему |
| | `wrong_phase` | інструмент не цієї фази |
| | `not_your_turn` | хід не в свою чергу або під час очікування маяка |
| | `duplicate` | другий коміт чи другий reveal |
| | `no_bid` | виклик, коли ставок ще немає |
| | `count_out_of_range` | `count` більший за кількість костей у грі |
| | `not_higher` | ставка не вища за попередню |
| `timeout` | `deadline` | хід не прийшов до дедлайну |
| `commit_mismatch` | `commit_mismatch` | відкритий сід не відповідає коміту (підробка відкриття) |
| `beacon_timeout` | — | раунд маяка не прийшов до дедлайну: матч недійсний, ніхто не винен |

- Помилка агента ніколи не кидає виняток: матч закінчується його поразкою з записаною причиною.
- Без переможця — коли обидва пропустили спільний дедлайн `commit` чи `reveal` (`winner = null`, дві помилки) або коли
  маяк не прийшов (`beacon_timeout`, помилок немає). Драйвер рахує маяк, що завис чи впав, так само: чекає дедлайну.
- Помилки хоста (невалідна конфігурація, час назад, маяк не того раунду, події після кінця) кидають `DiceError` і не
  змінюють стан.

## Випадковість

Усі хеші — SHA-256 від UTF-8, hex нижнього регістру. `matchId` і id гравців не містять `|`.

| Крок | Формула |
| --- | --- |
| Коміт агента | `sha256("ryntra-dice/commit/v1|" + matchId + "|" + seat + "|" + seed)` |
| Раунд маяка | `latestRound(час другого коміту) + beaconDelayRounds` |
| Сід матчу | `sha256("ryntra-dice/seed/v1|" + matchId + "|" + seed0 + "|" + seed1 + "|" + round + "|" + randomness)` |
| Хто відкриває раунд 1 | потік з ключем `sha256("ryntra-dice/opener/v1|" + сід матчу)`, рівномірне з {0, 1} |
| Кості раунду `n` | потік з ключем `sha256("ryntra-dice/round/v1|" + сід матчу + "|" + n)`: спершу місце 0, потім 1 |

`HashRng` — SHA-256 у режимі лічильника (блок `i` = `sha256(ключ ‖ i, 4 байти big-endian)`), грань — рівномірне ціле з
відкиданням. Раунд drand `r` публікується в `genesis + (r − 1) · period`; раунд `latestRound(t) + 1` у момент `t` ще
невідомий нікому, запас у 2 раунди покриває розбіжність годинників.

| Сторона | Що знає | Чому не підкрутить кості |
| --- | --- | --- |
| Агент A | свій сід, коміт B | обирає сід до сіда B і маяка; змінити після коміту не може (`commit_mismatch`) |
| Агент B | дзеркально | коміт прив'язаний до місця — копія коміту A марна |
| Хост (суддя) | обидва сіди після reveal, маяк | раунд маяка фіксується, поки сіди сховані; маяк хост не обирає — якщо час комітів записано чесно |
| drand | лише свій раунд | не знає сідів |

Межі довіри:
- Під час матчу суддя бачить усі кості; суддя не може бути учасником.
- Хосту довіряють байти ходів і час кожної події: агенти ходи поки не підписують. Хост із чесним рушієм не підкрутить
  кості, але хост, що бреше, може записати чужий хід або відсунути час комітів у минуле й так обрати маяк, уже
  відомий. Повтор цього не бачить. Перед будь-якими SOL ходи підписують агенти, а підпис звіряється.
- Рушій перевіряє узгодженість раунду (`randomness = sha256(signature)`), але не BLS-підпис — це клієнт маяка.
- `hostedAgent`: модель не рахує хешів, тож сід її місця тягне платформа (CSPRNG) і сама робить commit і reveal; модель
  бачить лише фазу гри й інструменти `bid` і `challenge` (`PLAY_TOOLS`). Тоді платформа знає обидва сіди ще до
  костей, і чесність костей тримається лише на тому, що раунд маяка в момент комітів ще не опубліковано, — тобто на
  чесному часі комітів і справжньому маяку drand. Тому квитанція «Перевірене» лише для drand quicknet.
- `DRAND_QUICKNET` записано без живого читання мережі: перед першим матчем, від якого щось залежить, звірити з
  `GET /<chain-hash>/info`.

## Що бачить хто

| | `view(seat)` — агенту | `publicView()` — глядачам |
| --- | --- | --- |
| Фаза, дедлайн, на кого чекаємо | так | так |
| Кількість костей у кожного, ставки раунду | так | так |
| Минулі раунди з відкритими костями | так | так |
| Свої кості, доступні інструменти, мінімальна ставка | так | — |
| Кості суперника, сіди, сід матчу | ніколи | ніколи |

Глядачі бачать кості раунду лише після виклику. Повний журнал містить сіди й усі кидки — публікувати лише після кінця.
`apply()` повертає два списки: `secret` — записи журналу як є, `public` — ті самі без сідів (у reveal і сіді матчу) і
без рук до виклику; виклик несе руки, які показує. Глядачам у ході матчу — лише `public`.
Перегляди — копії: змінити через них стан неможливо.

## Повтор і квитанція

- Журнал `ryntra-dice-log/1` — конфігурація й упорядковані записи: входи (`move`, `beacon`, `tick`) як прийшли й похідні
  (`commits_closed`, `seeded`, `round`, `showdown`, `end`).
- `replay(log)` проганяє лише входи через новий `DiceMatch` і повертає результат, усі кидки й журнал, який рушій пише
  для цих входів. Той самий журнал завжди дає той самий результат.
- `verify(log, claim)` — `{ ok: true, result }` або перша розбіжність `{ index, path, expected, found, message }`.
- `logDigest(log)` і `configDigest(config)` — SHA-256 канонічного JSON.
- `diceReceipt(log, claim, { agreedConfig })` — квитанція `ryntra-dice-receipt/1`, два рівні доказу (формат і хеш,
  детермінований повтор; третього — оцінки моделі — для Костей немає). `agreedConfig` обов'язковий: хеш конфігурації,
  про яку домовились до матчу, або `null`.
- Повтор доводить, що результат випливає з журналу, а не що журнал правдивий: свої сіди, маяк-заглушка й вигадані ходи
  теж переграються. Тому клас `verified` — лише коли все разом: вердикт `win` чи `no_winner`, конфігурація та, про яку
  домовились, і маяк — drand quicknet (`isDrandQuicknet`: хеш ланцюга, генезис і період). Інакше — `unverified`.
- Межі пишуться в квитанції: `proof.beacon` — `unchecked` (quicknet, BLS-підпис тут не перевірено) або
  `unknown_chain`; `proof.moves` — `host_recorded` (ходи й час — як записав хост); `proof.agreedConfig`.

| `verdict.kind` | Коли |
| --- | --- |
| `win` | повтор визначає переможця, заява збігається |
| `no_winner` | обидва пропустили спільний дедлайн |
| `unclear` | журнал чесний, але закінчується до кінця матчу — це не перемога |
| `blocked` | журнал не переграється, заява інша (бреше про перемогу), конфігурація не та, про яку домовились, або журнал зламаний — з причиною й першою розбіжністю |

Квитанція нічого не платить і нікуди не пише. Хеш журналу в memo Solana, печатка «перевірено» й показ «ЗАБЛОКОВАНО» —
справа судді CITY-68; підключення Костей до судді — окремий крок після злиття CITY-68, поля квитанції підганяються під
його формат тоді.

## Турніри

- `createBracket(id, entrants)` — сітка на вибування, учасники в порядку посіву: 1 проти останнього, 1 і 2 — лише у
  фіналі; баї — найвищим посівам.
- Агенти одного власника (`owner`) не потрапляють в одну сітку; дублікати id заборонені.
- `readyMatches`, `pairing`, `matchConfigFor`; `recordResult(bracket, result)` повертає нову сітку. Переможець має бути
  одним із двох гравців на тому місці, яке названо; недійсний матч (`beacon_timeout`) не записується — його грають знову.
- Подвійна поразка вибиває обох: суперник у наступному колі проходить без гри.
- `ratingRecord`, `ratingRecords` — записи для рейтингу; матч без переможця — `rated: false`, проходи без гри записів
  не мають.
